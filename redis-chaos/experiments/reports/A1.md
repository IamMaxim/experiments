# A1. Blackhole master dc1-s1 for 60s

Run: `experiments/runs/A1-20261020-165215`. Load: 400 ops/s SET, 16 closed-loop
workers, 1s response timeout, 3s overall, 3 retries.

## Cluster

| t | event |
|---|---|
| 5.0 | router drops every packet to/from dc1-s1 |
| ~11 | other nodes mark dc1-s1 PFAIL |
| ~13 | FAIL agreed; cluster_state fail on every node for ~2s |
| ~15 | dc2-s1 promoted (epoch 20); cluster_state ok again |
| 65.0 | heal; dc1-s1 sees the new epoch, becomes a replica of dc2-s1 |
| 72 | dc1-s1 replication link up |

Failover took ~10s from the cut (node-timeout 5s + FAIL propagation + election).
No acknowledged write was lost (dc1-s1 could not acknowledge anything while
cut off).

## Client

| t | event |
|---|---|
| 5–8 | requests to shard 1 hang; at 8.0 the first `io:timed out` after the 3s overall timeout |
| 8–65 | every shard-1 request times out: 16 workers × one 3s failure each per key. Shards 2 and 3 are healthy but throughput drops from 400 to ~15 ops/s because each worker is stuck 3s out of every ~3.2s (head-of-line blocking in the harness) |
| 15 | the cluster has a new master. The client does not notice: no log line, no refresh |
| 65 | heal. Still timeouts on shard 1 |
| 82.7 | load phase ends: 400 errors, all `io:timed out`, all shard 1; 2837 ok |
| 82.7–110 | verification GETs on shard 1 keep timing out (8 retries, 3.5s apart) |
| 110.8 | `beginning slot refresh` / `slot refresh complete`, verification finishes immediately after |

Recovery came 45.8s after the heal and only because a GET finally reached
dc1-s1 (now a replica), which answered MOVED.

## What happened in the library

1. A response timeout maps to `RetryMethod::RetryImmediately`. The request is
   re-queued with the same slot map, so it goes back to the same dead master.
   Three retries later it fails. Nothing marks the node as suspect, nothing
   refreshes the topology. The client stays on the old master for as long as
   the old master is unreachable, however long the failover took.
2. After the heal the connection to dc1-s1 was still useless for 45s. The TCP
   socket had unacknowledged data; Linux retransmits with exponential backoff
   (0.2s, 0.4s … 51s). After 60s of blackhole the next retransmit was due
   ~45s after the heal. Until it fired, the socket was "connected" and silent,
   so every request on it timed out. Only when the retransmit got through did
   the MOVED arrive and the slot refresh run. The library never reconnects on
   a timeout, and sets no `TCP_USER_TIMEOUT` or keepalive by default.

## Went well

- Cluster side: clean failover in 10s, no lost writes, old master rejoined
  as a replica without manual help.
- Shards 2 and 3 never errored.

## Went wrong

- 57s of write unavailability on shard 1 while the cluster was healthy from
  t=15 onwards (42s of it with a master the client simply never looked for).
- 45s more after the heal while the stale socket waited for TCP backoff.
- The error the application sees is a bare `timed out`; there is no hint that
  the topology moved.

## Implications for redis-rs

- Timeouts need to feed topology discovery: after N consecutive timeouts on a
  node (or one timeout on a request whose slot owner has not been checked
  recently), refresh slots from a *different* node and reconnect to the
  suspect one.
- A periodic topology check (every few seconds, cheap `CLUSTER SLOTS` to a
  random healthy node) would have bounded the outage to the failover time.
- Set `TCP_USER_TIMEOUT` (or document it) so a blackholed socket errors out
  instead of surviving for minutes; alternatively drop a connection after
  consecutive timeouts.
