# A8. `CLIENT PAUSE 30000 WRITE` on master dc1-s1 (slow node, bus alive)

Run: `experiments/runs/A8-20261020-170258`. Mixed load (50% GET). The master
keeps answering reads and the cluster bus, but holds every write for 30s.

## Cluster

Nothing. The node is healthy from the cluster's point of view the whole
time; no PFAIL, no failover.

## Client

First `io:timed out` at 8.0s; 144 timeouts over the 30s; every one on shard 1
and every one a write. Reads to shard 1 succeeded whenever a worker got to
one (the closed-loop harness shows s1 ok=0 only because the 16 workers were
all stuck in 3s write timeouts most of the time).

No library log lines: timeouts trigger nothing.

## Reading

There is nothing a topology refresh could have done here: the cluster had no
better master to offer. This case is the argument for *not* reacting to a
single timeout with a full refresh, and for keeping the reaction cheap
(refresh from another node, compare, do nothing if unchanged).

The cost the client pays is the harness's: each write burns the full 3s
overall timeout (1s × 3 attempts to the same node). A per-node "circuit
breaker" that fails fast after N consecutive timeouts would have turned 30s
of 3s stalls into 30s of immediate errors, which is usually what a caller
wants from an unresponsive shard.

## Implications for redis-rs

- Timeouts to a node should be counted; after a threshold, requests to that
  node fail fast (or go to a replica for reads) until a probe succeeds.
- Retrying a timed-out request immediately on the same node is wasted time
  in every scenario so far; the first retry after a timeout should at least
  go through a topology check.
