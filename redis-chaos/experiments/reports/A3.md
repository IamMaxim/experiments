# A3. kill -9 master dc2-s2, leave it dead for 60s

Run: `experiments/runs/A3-20261020-165409`. Load: 400 ops/s SET, 16 closed-loop
workers, defaults (1s/3s timeouts, 3 retries).

## Cluster

| t | event |
|---|---|
| 5.1 | `docker kill -s KILL rc-dc2-s2`; its network namespace disappears with it |
| 6.7 | both replicas report `master_link_status: down` |
| ~12 | PFAIL → FAIL; dc1-s2 wins the election (epoch 22) |
| 17 | all nodes agree: dc1-s2 is master of 5461–10922 |
| 65 | `docker start`; dc2-s2 comes back, joins as replica of dc1-s2, link up at ~70 |

Failover in ~7–10s. No lost writes.

## Client

| t | event |
|---|---|
| 5.0 | `connection to 10.77.22.10:6379 lost; repairing in background` (EOF/reset). First reconnect attempts get `Connection refused` (the kernel still answered), then `timed out` once the namespace was gone |
| 5.0–14.1 | **12 slot refreshes in 9s**, one per second, each preceded by one or more 1s connect attempts to the dead node |
| 6–14 | total throughput 0–12 ops/s **on all three shards**; p50 latency on the healthy shards 1 and 3 is 1000–2000ms |
| 8–14 | 25 shard-2 requests time out (3s overall) |
| 15 | new master in the slot map; shard 2 serving again |
| 16 | one last burst: 9 timeouts spread over all shards, max latency 2.28s |
| 17–80 | clean, 400 ops/s |

Total: 32 errors, 2284ms worst latency, ~10s of near-total outage.

## What happened in the library

1. The dead connection is detected immediately (reset → `Reconnect`), and the
   per-request fallback picks another node of the shard (a replica). The
   replica answers MOVED to the *old* master address, which is still what the
   topology says. MOVED means `RebuildSlots`, so a slot refresh starts.
2. `refresh_slots` takes the connection map **write lock** for its whole
   duration. After reading `CLUSTER SLOTS` it calls
   `refresh_connections_locked`, which checks or creates a connection to
   every node in the map, including the dead one. That connect attempt waits
   the full `connection_timeout` (1s). While the write lock is held no request
   can get a connection (`get_connection` needs the read lock), so **every
   shard stalls for ~1s per refresh**.
3. Each stalled request then gets routed with the still-stale map, lands on
   the replica again, gets MOVED again, and triggers the next refresh. This
   repeats once per second until the cluster finishes the failover and
   `CLUSTER SLOTS` finally names a reachable master.
4. The `reconnect_loop` for the dead node also keeps trying with 1s connects
   (backoff 50ms → 1s); that part is harmless on its own.

## Went well

- Detection was instant and the client recovered on its own within ~2s of
  the cluster electing a new master. Nothing needed the heal.
- The node coming back 60s later caused no errors at all.

## Went wrong

- One dead node out of nine made the whole client unusable for 10s: healthy
  shards saw 1–2s latencies and a throughput collapse, not because of
  anything in the cluster but because the refresh holds a global lock while
  dialing a dead host.
- The MOVED → refresh → stale map → MOVED loop generates a refresh per
  request burst; with more client instances this is a `CLUSTER SLOTS` storm
  on the surviving nodes.

## Implications for redis-rs

- Do not hold the connection-map write lock while establishing connections.
  Refresh the slot map, swap it in, and repair connections outside the lock
  (or with per-node locks).
- Skip nodes that are currently `Reconnecting` during a refresh instead of
  dialing them synchronously.
- Rate-limit slot refreshes (coalesce requests, minimum interval) and
  remember that a MOVED pointing at a node that is known-dead is not news.
