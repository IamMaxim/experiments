# A5. Graceful stop (SIGTERM) of master dc1-s1, start after 30s

Run: `experiments/runs/A5-20261020-170045`. `docker stop` sends SIGTERM; Redis
writes its AOF and exits, closing client sockets. The container's network
namespace goes with it, so later connects time out rather than being refused.

## Cluster

Replica links down at ~6s, FAIL and election at ~12s, dc2-s1 promoted. At
35s dc1-s1 restarts, finds the newer epoch, joins as a replica. No lost
writes.

## Client

| t | event |
|---|---|
| 5.4 | connection to dc1-s1 lost (EOF) → reconnect in background; slot refresh |
| 6.7 | **13 `MOVED <slot> 10.77.11.10:6379` errors returned to the application** on shard 1 |
| 7.7 | 3 more MOVED errors |
| 8.7–13.7 | one slot refresh per second; shards 2 and 3 at 1–2s p50 latency and a few ops per second (the A3 lock stall) |
| 9.7–13 | 14 shard-1 timeouts |
| 14 | new master in the map, throughput back |

30 errors: 16 MOVED, 14 timeouts. Outage ~9s on shard 1, ~8s of degraded
service on the other two.

## What happened

The interesting part is the MOVED errors. Sequence for one request:

1. attempt 1: sent to dc1-s1, connection drops → `Reconnect`, retry 1;
2. attempt 2: dc1-s1 is `Reconnecting`, the fallback picks a replica of the
   shard; the replica (which still believes dc1-s1 is master) answers
   `MOVED slot 10.77.11.10` → `Retry::Immediately` with the redirect,
   `RebuildSlots`, retry 2;
3. attempt 3: redirect to 10.77.11.10 needs a connection; the connect times
   out (1s) → retry 3;
4. attempt 4: replica again → MOVED again, but `retry == number_of_retries`,
   so the MOVED error itself is handed to the caller.

The retry budget is shared between "the node is dead" and "follow this
redirect", and when it runs out the last server error is surfaced verbatim.
The application gets a redirect it cannot act on.

The rest is A3: refresh storms, global lock stall, until the cluster elects a
new master.

## Went well

- Detection instant (EOF), recovery ~2s after the election, no manual heal
  needed; the node returning 30s later caused no errors.

## Went wrong

- MOVED leaked to the application.
- A healthy-but-stale replica answering MOVED to a dead address is taken as
  news every time, causing a refresh (and a 1s global stall) per burst.
- Healthy shards degraded for ~8s.

## Implications for redis-rs

- A MOVED/ASK to an address that is currently unreachable should not consume
  the caller's retry budget the same way as a failed attempt, and a redirect
  error should never be the final error returned to the caller (map it to an
  "unavailable" error).
- The reconnect-loop knowledge ("10.77.11.10 is dead") should be consulted
  when a MOVED points at it: back off and refresh from elsewhere instead of
  dialing it inline.
- Same lock fix as A3.
