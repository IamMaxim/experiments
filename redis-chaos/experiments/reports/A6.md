# A6. `docker restart` of master dc1-s1 (back within node-timeout)

Run: `experiments/runs/A6-20261020-170138`. The node was down ~1.5s, so no
failover: it came back as master with the same epoch.

## Cluster

5.8s connections drop; ~7s dc1-s1 is up again but reports `cluster_state
fail` for ~2s while it re-syncs with the others; 9s ok; replicas relinked by
11s.

## Client

| t | event |
|---|---|
| 5.8 | connection lost → reconnect loop; slot refresh |
| 7.0 | `reconnected to 10.77.11.10:6379` |
| 7.1–8 | 16 × `CLUSTERDOWN The cluster is down` returned to the application (shard 1) |
| 9 | clean |

16 errors, max latency 1.28s, no lost writes.

## What happened

CLUSTERDOWN maps to `WaitAndRetry`: sleep `wait_time_for_retry(1)`, which is
`rand(min_wait=1280ms .. clamp(2^1*10))`, so ≥1.28s, then retry. With a 3s
overall timeout there is room for one such retry; the second CLUSTERDOWN
exhausts the budget (one attempt + one sleep + one attempt ≈ 2.6s, the next
sleep would exceed 3s), and the error is returned.

The node was fine ~2s after restart, so the errors are the price of the
retry schedule, not of the cluster.

## Went well

- 1.5s outage, 1.2s to reconnect, no refresh storm (the slot map never
  changed), no lost writes.

## Went wrong

- `DEFAULT_MIN_RETRY_WAIT_TIME = 1280ms` is a very coarse first backoff for a
  condition that clears in a second or two; with the library's default
  overall timeout (= response timeout, 1s here) not even one retry fits, and
  every CLUSTERDOWN becomes a user-visible error.

## Implications for redis-rs

- Start the CLUSTERDOWN/TRYAGAIN backoff much lower (tens of ms) and grow it;
  the current minimum of 1.28s is larger than most transient conditions.
- Consider refreshing the slot map on CLUSTERDOWN from a *different* node:
  in other scenarios (D4) the node answering CLUSTERDOWN is the one that
  lost quorum, and waiting on it is pointless.
