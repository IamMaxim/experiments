# A9. Busy Lua script for 15s on master dc1-s1

Run: `experiments/runs/A9-20261020-170352`. `EVAL` with a 15s busy loop.
Expected the cluster bus to be blocked as well and a failover to follow.

## Cluster

**No failover.** The epoch never changed. While a script is busy, Redis keeps
serving file events (it must, to answer `BUSY` and accept `SCRIPT KILL`), and
the cluster bus links are file events too, so PINGs got their PONGs and
nobody marked the node failed. Only the cron-driven work stopped. The status
snapshots show the router's `redis-cli` timing out at 6.7s (`DOWN`) and a
garbled row at 12s (the `BUSY` reply), then normal at 21s.

## Client

| t | event |
|---|---|
| 5–10 | writes to shard 1 hang, then `io:timed out` (16, the first 3s batch) |
| 10.0 | `lua-time-limit` (5s) passed: `BUSY Redis is busy running a script` |
| 10–20 | **1266 `BUSY` errors in 10s**, returned immediately; shards 2 and 3 unaffected (full 400 ops/s minus shard 1) |
| 20.0 | script ends, shard 1 serves again |

1282 errors, 0 lost writes.

## What happened in the library

`BUSY` is not a known `ServerErrorKind`; it is an `Extension` error and maps
to `RetryMethod::NoRetry`, so each request fails instantly. That is why the
error count is high and the latency is low: the harness was not stalled.

## Reading

- A node can be unusable for clients while perfectly healthy for the
  cluster. No topology-based recovery applies; only client-side policy does
  (fail fast, or read from a replica).
- Fail-fast on BUSY is defensible. Treating BUSY like `TRYAGAIN`
  (`WaitAndRetry`) would have hidden a 10s outage behind the overall
  timeout instead of surfacing it; arguably the right choice is a short
  bounded retry, then surface. Worth deciding deliberately rather than by
  omission.
- Reads with a replica strategy would have continued (not measured here;
  see B/G3).

## Implications for redis-rs

- Add `BUSY` to the known server errors and give it an explicit policy.
- Same fail-fast-on-consecutive-timeouts point as A8 for the first 5s.
