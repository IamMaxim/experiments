# D4. Split brain: master dc1-s1 cut from every other node, still reachable by the client

Runs: `D4-20261020-170435` (1000 keys), `D4b-20261020-170702` (100 000 keys,
each written at most once), `D4c-20261020-170756` (same, no overall timeout).

The router drops traffic between dc1-s1 and the other 8 nodes only. The
client keeps a working path to dc1-s1.

## Cluster

| t | event |
|---|---|
| 5.0 | cut |
| ~11 | both sides mark the other PFAIL |
| 13.5 | the majority marks dc1-s1 FAIL; dc1-s1, alone, marks everyone else PFAIL and goes `cluster_state fail` (minority: it has seen no majority of masters for node-timeout) |
| 15.8 | dc2-s1 elected master of 0–5460 (epoch 37) |
| 35 | heal; dc1-s1 learns the epoch, becomes replica of dc2-s1, discards its own data set and resyncs |

## Client

| t | D4 / D4b (3s overall timeout) | D4c (no overall timeout) |
|---|---|---|
| 5–13.5 | **writes to shard 1 succeed and are acknowledged by dc1-s1**, which has no replica to send them to | same |
| 13.5 | dc1-s1 starts answering `CLUSTERDOWN The cluster is down` | same |
| 14.5 / 15.9 | first error seen by the application: `io:timed out` | first error: `ClusterDown` |
| 15–35 | 16 timeouts per 3s on shard 1, shards 2/3 starved by head-of-line | 84 `ClusterDown`, each after ≥1.28s + ≥2.5s of library sleeps (max latency 3.8s) |
| 35.5–35.9 | slot refresh, triggered by the first MOVED from the demoted dc1-s1 | same |
| verify | D4: 0 lost (every key rewritten after the heal masks it). **D4b: 847 lost. D4c: 943 lost** | |

The lost keys are exactly the ones acknowledged between the cut and the
CLUSTERDOWN switch (seq 127–128 for the first lost keys, i.e. ~8s into the
run).

## What happened in the library

1. In the 8.5s window the client wrote to a master that could not replicate.
   Nothing on the client side can know this; Redis Cluster's design accepts
   it (async replication, writes are lost when the minority master is
   demoted). `WAIT 1 <ms>` after each write would have caught it, at a cost.
2. From 13.5s dc1-s1 says CLUSTERDOWN. redis-rs maps it to `WaitAndRetry`:
   sleep ≥1.28s, **retry on the same node**. The new master was reachable
   and one `CLUSTER SLOTS` away from 15.8s on. The client never asked.
3. With the 3s overall timeout the CLUSTERDOWN never reaches the caller: the
   first attempt gets CLUSTERDOWN, the retry sleep is 1.28–2.5s, the second
   attempt gets CLUSTERDOWN, the next sleep overruns the budget and the
   request is reported as `timed out`. The caller cannot tell this apart
   from A1.

## Went well

- Redis did the right thing: the minority master stopped taking writes
  after node-timeout, the majority elected a replica, the old master was
  demoted cleanly on heal.

## Went wrong

- ~900 acknowledged writes lost (cluster design; the client can only
  mitigate with `WAIT`).
- 20s of shard-1 unavailability while a reachable master existed, because
  CLUSTERDOWN from a node does not make the client look elsewhere.
- The overall timeout hides the server's error.

## Implications for redis-rs

- On CLUSTERDOWN (and MASTERDOWN / TRYAGAIN), refresh the slot map from a
  node *other than the one that answered* before retrying; a node reporting
  the cluster down is the least qualified source for the topology.
- When the overall timeout expires after a server error was seen, return
  that error (or wrap it) rather than a bare timeout.
- Lower the minimum retry sleep (1.28s) so the first retry is cheap.
